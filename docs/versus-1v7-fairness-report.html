1v7 围攻问题：根因与修复

结论先行：不是 AI 变聪明了，而是模式本身被一个特例改成了 1v7。项目设计的对抗模式是 4v4，AI 补位到每队 4 人；但今天的一个提交把「单人开局」单独拎出来，硬编码成「0 个友军 + 7 个敌人」。你看到的围攻，是这个特例的直接结果——顺带还暴露了三个此前被 1v7 掩盖的底层缺陷。

模式 VERSUS 4v4（AI 补位） 证据 git 历史 + 真实浏览器活体探针 改动 src/main.js · src/entities/enemy.js

一、这个模式本来应该是什么样

设计文档里写得很明确，大厅文案也是这么写的——只有代码走偏了。

docs/MULTIPLAYER-DESIGN.md § VERSUS 4v4 — designed, locked

Players
2–8 human (up to 4 per team)
AI fills
Each team is padded to 4 combatants with AI bots; e.g. 2 humans + 2 bots per side
AI soldiers
Up to 8 bots total (4 per team), fewer when more humans join
Objective
Team deathmatch, 50 kills or 6 minutes; friendly fire off

大厅文案（index.html:436）也一直是这个口径：「2–8 名玩家分为蓝红两阵营（每队至多 4 人），不足由 AI 士兵补足」。

所以你一个人进房，正确结果应该是：你 + 3 个友军 AI，对 4 个敌方 AI

这才是「按正常模式配机器人」的结果。7 个 AI 全是敌人，那是另一个模式，不是这个模式。

二、根因：一个 4 行的特例

git 历史能精确指出是哪次改动引入的，以及它的原话。

commit 6fb9d01  2026-10-21
feat(versus): solo 1v7, full-map spawns, 20s no-fire deployment
- solo host fills seven hostile bots instead of 3 allies + 4 enemies

被它改掉的那几行（src/main.js · startVersusBots）

  const solo = Object.keys(teams || {}).length === 1;      ← 特例开关
  for (let team = 0; team < 2; team += 1) {
    // Solo VERSUS: one human vs seven hostile bots, not 3 allies + 4 enemies.
    const fill = solo
      ? (team === 0 ? 0 : 7)                                ← 0 友军 / 7 敌
      : Math.max(0, VERSUS_TEAM_SIZE - counts[team]);        ← 正常补位逻辑（被绕过）
  }

非 solo 分支的 Math.max(0, VERSUS_TEAM_SIZE - counts[team]) 本来就是正确的 4v4 补位——它只是被上面的特例抢先短路了。

1 人进房
solo = true
team 0 补 0 个
玩家独占蓝队
team 1 补 7 个
7 个 bot 全是敌人
于是「被围攻」
不是 AI 变聪明
而且这个特例还顺带掩盖了三个底层缺陷——因为在 1v7 里「同队 bot」根本不存在，友军误伤、复活无敌、bot 复活点聚簇都没机会暴露。改成 4v4 补位后，它们立刻全部现行（见第四节）。

五、征服制回合制：整个循环从未运行过

这是 1v7 改回 4v4 之后才浮出水面的问题——它不属于 1v7，而是回合制本身。

问题一：回合循环是个死函数

25 分制的得分只来自控制点占领收入（每点每 2 秒 +1 分），击杀虽然也计 1 分，但单独凑不满 25 分。而驱动这一切的 updateConquest(dt) ——占领进度、占领收入、回合时钟、橡皮筋——被定义了，却从来没有被调用过。

后果：时钟不走 → 点永远不翻 → 得分恒为 0 → 回合永远不会结束。实测 50 秒整局控制点归属始终是 ---，得分始终 [0,0]。

（1v7 时红队 bot 会自然聚在场地中心，顺带白占了 3 个点——之前那份报告里「点数经济失衡」的结论，其实也是这个 bug 的副作用，不是设计。）

问题二：AI 里根本没有「去占点」这种行为

检索 src/systems/ai/ 与 src/entities/enemy.js 找不到任何 controlpoint / capturepoint / conquest 逻辑。就算接上时钟，也没人会去站点。

修法

① 接上 updateConquest(dt)（host 专属）。

② 新增「占点兵」：每阵营一名士兵带着控制点路点过去驻守；A* 寻路目标链也改为优先走这个点；抵达后原地站住（占领需要 6 秒无人争夺的持续在场）。

③ 派工规则：两阵营各取一端，永不抢同一个点。被双方同时占据的点会被冻结（谁都不计分），两边都去抢同一个点会让回合卡死在 0:0。中间的点留作最后手段，也是留给人类去争的中立奖品。

④ 点位放在两队出生点之间（你选的方向）：每队 4 个锚点其实散布全图，真正的「中间」不是一条线，而是两队锚点几乎相邻的三处收窄区——正是两队真正会遭遇的地方。选点后两边走到任一点的距离完全相等（20.2 / 38.9 / 20.1 米），所以换边之后依然公平。

点位坐标蓝队(侧0)路程红队(侧1)路程
west（双方各取一端）(-85, 29)20.2 m20.2 m
mid（中立奖品，留给人类）(-36, 23)38.9 m38.9 m
east（双方各取一端）(89, -62)20.1 m20.1 m

调试中修掉的四个「到不了点」的原因

① 派工每 0.3 秒重选 runner → 占领计时不断被重置 → 改成粘性分配（runner 一直守着同一个点）。

② 各角色的交战距离（flank 17m / hold 20m / suppress 26m）把 runner 挡在圈外 → 占点兵豁免。

③ A* 寻路段覆盖移动方向，把 bot 导向战斗目标而不是控制点 → 寻路目标链加入占点路点。

④ 软锁守卫把驻守的 runner 传送走：bot 站在点上一动不动超过 7 秒就被判定「卡住」并强制挪位，占领计时因此永远完不成 → 占点兵豁免这条守卫。

现在的实测：完整的一回合

t=9.8 红方占下 east 点 → t=10.1 蓝方占下 west 点 → 双方各每 2 秒 +1 分，比分交替上升 → t=48 25 : 22，蓝方拿下回合 → t=54 换边重开，点位与得分重置，新回合重新抢占。

中间那个中立点双方都不主动去抢——它是留给你的。站上去占住它，你那队就能从 1 分/2 秒变成 2 分/2 秒，这也是这个模式里人类真正能翻盘的地方。
